The brief
Build Slotbook: hosts publish when they are free, guests book a slot, and nobody is ever
double-booked — even when the network, the clock or the user misbehaves.
Think of it as a small Calendly whose booking engine you would trust with money. The
core is a full-stack TypeScript app on Postgres. A clean, reliable core matters more than a
long feature list, so build the core and its reliability first, then pick from the optional
extensions if you have time.
Timebox: the core is sized for about 4–5 hours with an AI coding assistant. Optional
extensions are on top of that.
AI tools: Claude, Cursor, Copilot or anything else — use them as much as you like.
Deadline: submit within 72 hours of receiving this brief.
Unfinished work: fine. Write down what is missing and why in your report.
Core features
Three surfaces: a host dashboard, a public booking page per event type, and a JSON API
that both use.
Host (authenticated — a seeded login or magic link is fine)
1. Set a home time zone (IANA, e.g. Asia/Kolkata , America/New_York ).
2. Create event types: name, slug, duration (15–120 min), capacity (1 = one-on-one, more
than 1 = group session), buffer before and after (0–30 min), minimum notice (e.g. 4 h)
and booking horizon (e.g. 30 days).
3. Define weekly availability in the host's time zone (e.g. Mon–Fri 09:00–17:00, several
windows per day allowed) plus date overrides (a day off, or custom hours on one
date).
4. See upcoming bookings and cancel one with a reason.
Guest (public, no login)
1. Open /{host}/{event-slug} and see available slots for the next 30 days in their
browser time zone, with a time-zone switcher.
2. Pick a slot — it is held for 5 minutes while they enter name and email.

Booking lifecycle
A booking moves held → confirmed → optionally cancelled . A hold that is not
confirmed in time becomes expired . Capacity counts holds and confirmed bookings,
never expired or cancelled ones.
Notifications
On confirm, reschedule and cancel, emit an event to a notifications sink. A real email
provider is not needed — writing to a table or posting to a local webhook receiver is
enough.
Minimum API (shape it as you like, but document it)
Tech constraints and scope
Language: TypeScript end to end.
Database: Postgres 15+ (local Docker or Supabase). Postgres is the source of truth for
correctness — no Redis or external lock service.
Framework: your choice — Next.js, Remix, or a Node API (Fastify, Hono, Express) with
a React frontend. Any ORM or plain SQL.
One-command run: docker compose up (or pnpm i && pnpm dev against a
compose-provided Postgres) starts the app, runs migrations and seeds a demo host
with two event types.
UI: plain and clear is fine; polished visual design is not required.
