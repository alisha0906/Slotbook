Slotbook — Engineering Report

A small, reliable Calendly-style booking engine. Hosts publish availability, guests book slots, and nobody is ever double-booked — even under concurrent requests, clock skew, or a misbehaving client. Postgres is the single source of truth for correctness.

How a booking request flows (the hot path):

  • Guest opens /{host}/{event-slug}. The SPA calls GET /api/hosts/{host}/events/{slug}/slots?tz=....
  • The API loads the event type + its weekly rules and date overrides, generates candidate slots in UTC (time-zone aware), subtracts active holds/confirmed per slot, and returns only slots with remaining capacity.
  • Guest picks a slot → POST /api/holds with an Idempotency-Key. The API opens a transaction, takes a Postgres advisory lock keyed on (event_type_id, slot_start), checks idempotency, checks capacity, inserts a held row with hold_expires_at = now() + 5 min, commits.
  • Guest enters name/email within 5 minutes → POST /api/holds/{id}/confirm. Status flips to confirmed; a booking_confirmed row is written to the notifications sink; the guest receives a private manage_token.
  • reschedule and cancel move or cancel the booking, each emitting a notification.
  • A background worker sweeps expired holds to expired every 30 s. Correctness does not depend on it (see §5).

Single-origin deployment. The production image builds the React app and Fastify serves the static bundle, so the whole app lives on localhost:4000 with no CORS and one port.

3. Data model

All instants are stored as timestamptz (UTC). Availability is stored as local wall-clock time plus the host's IANA time zone, and converted to UTC instants at slot-generation time.

Status enum: held → confirmed → cancelled; an unconfirmed hold becomes expired. Capacity counts only confirmed and non-expired held rows — never expired or cancelled.

Constraints that back correctness:

  • Unique (event_type_id, idempotency_key) — a retried hold creates at most one row.
  • Unique, random manage_token — the guest's capability link is unguessable.
  • Index (event_type_id, slot_start, status) — fast capacity counts per slot.

4. Key decisions

  • Postgres advisory locks for no-double-booking (vs. unique index / SERIALIZABLE). A partial unique index works for capacity = 1 but not group capacity > 1. SERIALIZABLE adds retries and cross-slot contention. A transaction-scoped advisory lock keyed on (event_type_id, slot_start) serializes only the requests that actually contend, handles any capacity, and needs no first row to lock.
  • Expiry is advisory, not load-bearing. Capacity queries treat a held row with hold_expires_at ≤ now() as free, so a hold stops consuming capacity the instant it expires, whether or not the sweep has run.
  • Idempotency inside the slot lock. The Idempotency-Key row is unique per (event_type_id, key), and the check runs after the lock, so a retried request resolves to the existing hold rather than racing capacity (a real bug we fixed — see §5 / AI_LOG).
  • Store wall-clock availability + IANA zone; convert to UTC per date. Storing availability as UTC would break across DST. Local time + zone, converted per date with Luxon, keeps 09:00 at 09:00 local year-round and shifts the UTC instant at DST boundaries (see §6).
  • Node (Fastify) + React (Vite), single-origin. A small Fastify API with explicit SQL transactions keeps the correctness-critical code obvious; serving the built SPA from the same server removes CORS and gives a one-URL demo.
  • Server re-validates every requested slot. Clients send an explicit slotStart; the server regenerates the schedule and confirms the instant is genuinely bookable (within notice + horizon) before holding.
  • Seeded "token = host id" auth, documented as a gap. The brief permits a seeded login. Full sessions/JWT + password hashing are out of core scope; the simple token still enforces the public-vs-host boundary and host-scoping of queries.

6. Time zones (with a DST worked example)

Generation. Availability is stored as local wall-clock windows (e.g. Mon–Fri 09:00–17:00) in the host's IANA zone. To produce slots we walk each calendar day in the host zone, build each window's start/end as a Luxon DateTime in that zone (so the correct UTC offset for that date is applied), then convert to UTC. Candidate starts step by duration + buffers.

Display. Slots are returned as UTC instants plus a localized label; the guest page converts UTC → the chosen browser zone, with a time-zone switcher.

Worked DST example — America/New_York spring-forward, 9 March 2025. On that date clocks move forward: 02:00 EST (-05:00) jumps to 03:00 EDT (-04:00), so wall-clock 02:00–02:59 does not exist.

  • A 09:00 local slot before DST (Fri 7 Mar 2025) is EST -05:00: 09:00 -05:00 → 14:00Z.
  • A 09:00 local slot after DST (Mon 10 Mar 2025) is EDT -04:00: 09:00 -04:00 → 13:00Z.

So the same "9 AM" availability correctly maps to a different UTC instant across the transition — the engine never hard-codes an offset. If a window ever covered the skipped hour, Luxon resolves the non-existent local time forward, and because slots must fit entirely inside the window, no impossible slot is emitted. (Observed live: a November New York slot returns startLocal ...T09:00:00-05:00 → startUtc ...T14:00:00Z, i.e. EST, as expected.)

7. Optional extensions

None of the optional extensions were built — the time was spent making the core and its reliability solid (concurrency-safe capacity, idempotency, DST-correct slots, the real-Postgres concurrency suite). The architecture leaves clear seams:

  • Waitlist / reminders / webhooks fit naturally on the existing notifications sink and the bookings lifecycle.
  • Daily cap / per-guest limit are additional checks inside the same hold transaction.
  • Observability — a /health endpoint already exists; structured logs via Fastify's logger are in place.

8. Testing

  • Covered: the concurrency/reliability core — single-seat race, group capacity, idempotency under concurrency, and a sequential full-slot block — all against a real Postgres.
  • How to run: 
    docker compose up -d db
docker compose run --rm --build tests
  • Results: 4/4 passing — capacity-1 race (50 → 1), capacity-5 race (40 → 5), idempotency (20 same-key → 1 booking), sequential sanity.
  • Gaps: unit tests for slot generation / DST edges, end-to-end browser tests, and a k6/Artillery load test with p95 numbers. Slot logic was verified by hand against the running API.

9. Using AI

See AI_LOG.md for detail. In short: AI was strong at scaffolding, schema + constraints, and the Luxon time-zone math, and weak at runtime edge cases that only appear when the code runs — a pg Date | string quirk, an idempotency-vs-capacity ordering race (caught by the concurrency test), and a frontend header-merge bug that dropped Content-Type. Every bug was found by running the stack, so the loop was build → run → verify on each step.

10. Known gaps and next steps

  • Auth is seeded/simple. Host "token" is the host id and passwords are compared in plain text (the brief permits a seeded login). Next: hash passwords, issue signed, expiring sessions, invalidate on logout.
  • Host CRUD is partly via seed. Event-type and availability editing are seeded rather than exposed as full dashboard forms; the tables and API support adding them.
  • No optional extensions yet (waitlist, reminders, .ics, webhooks, etc.).
  • Test depth. Add unit tests for slot generation (including DST), Playwright e2e for the guest flow, CI on every push, and a k6 load test with throughput / p95 / error-rate numbers.
  • Observability. /health and structured logs exist; add request IDs and basic metrics (bookings, hold expiries, notification lag).

With another day: password hashing + real sessions, host availability editing UI, a waitlist built on the notifications sink, and a k6 load test with reported p95 latency.
